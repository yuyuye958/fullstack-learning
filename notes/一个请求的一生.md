> 追踪对象：`fullstack-mall` 后端公开商品详情接口。
> 代码位置：`C:\Develop\private\fullstack-learning\apps\fullstack-mall\backend`
> 运行方式：`local` profile（H2 内存库，商品详情缓存关闭），端口 8080。
> 本文所有类名、方法名、行为均来自真实代码与真实调用结果；标注「实测」的均在本机跑过。

## 2. 逐层拆解

### 第 1 层：Tomcat —— 把字节变成 `HttpServletRequest`

- 类：Spring Boot 内嵌 `TomcatWebServer`（日志 `Tomcat started on port 8080 (http) with context path '/'`）。
- 负责什么：监听 8080、解析 HTTP 报文、把请求交给 Servlet 容器、最后把 `HttpServletResponse` 写回字节。
- 前端视角最容易误解：**「后端服务」不是一个函数，而是一个常驻进程 + 线程池。** 你本地 `mvn spring-boot:run` 的进程活着，端口才可用；进程一停，`curl` 立刻 `Connection refused`（本机实测过：计划任务停止后 `无法连接到远程服务器`）。

### 第 2 层：Filter 链 —— 在进入业务代码之前

#### 2.1 `TraceIdFilter`

文件：`service/src/main/java/com/example/fullstackmall/service/common/trace/TraceIdFilter.java`

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {
    public static final String TRACE_ID_HEADER = "X-Trace-Id";

    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) {
        String traceId = resolveTraceId(request.getHeader(TRACE_ID_HEADER));
        request.setAttribute(TRACE_ID_ATTRIBUTE, traceId);
        response.setHeader(TRACE_ID_HEADER, traceId);
        filterChain.doFilter(request, response);
    }

    private String resolveTraceId(String candidate) {
        if (candidate != null && VALID_TRACE_ID.matcher(candidate).matches()) {
            return candidate;      // 合法则透传
        }
        return UUID.randomUUID().toString().replace("-", "");   // 否则服务端生成
    }
}
```

- 负责什么：给每次请求一个链路 ID。前端可以在请求头带 `X-Trace-Id`，服务端校验 `[A-Za-z0-9_-]{8,64}`，不合法就自己生成，并同时写进 request attribute 和 response header。
- `TraceIdContext.get(request)` 再从 attribute 里取出来，塞进响应体。
- 前端视角最容易误解：**traceId 不是前端生成的业务 ID，而是排查用的关联 ID。** 报错时把它（响应头 `X-Trace-Id` 或 body 里的 `traceId`）发给后端，后端就能在日志里定位到这一条请求。实测响应里 `traceId` 是 32 位无横线 UUID。

- 前端视角最容易误解：
  1. **「接口 200 但数据为空」通常是权限规则放行了，业务层查不到数据，而不是 token 没带。**

### 第 3 层：`DispatcherServlet` —— 找哪个方法处理

- 组件：Spring MVC 的 `DispatcherServlet` + `RequestMappingHandlerMapping`。
- 匹配依据：`ProductController` 类上的 `@RequestMapping("/api/products")` + 方法上的 `@GetMapping("/{id}")`。
- 负责什么：URL → HandlerMethod 的映射，以及后面的参数解析、返回值处理。
- 前端视角最容易误解：**路由是「服务端路由表」，和你前端 Vue Router 完全无关。** `/api/products/1` 里的 `1` 是 `@PathVariable`，不是 query 参数；写成 `/api/products?id=1` 会 404。

### 第 4 层：`ProductController` —— HTTP 适配层

文件：`service/src/main/java/com/example/fullstackmall/service/product/ProductController.java#L24-L50`

```java
@RestController
@RequestMapping("/api/products")
@Tag(name = "公开商品")
public class ProductController {

    @Resource
    private IProductFacade productFacade;

    @GetMapping("/{id}")
    @Operation(summary = "查询已上架商品详情")
    public ApiResponse<ProductDetailResponse> detail(
            @PathVariable Long id,
            HttpServletRequest servletRequest
    ) {
        ProductDetailResponse response = productFacade.getPublishedProduct(id);
        return ApiResponse.success(response, TraceIdContext.get(servletRequest));
    }
}
```

- 负责什么：只做三件事——接参（`@PathVariable Long id`）、调用例（`IProductFacade`）、包统一返回体（`ApiResponse.success`）。**没有业务判断，没有 SQL。**
- 依赖的是 `contract` 模块里的接口 `IProductFacade`，不是实现类。这是模块边界。
- 前端视角最容易误解：
  1. Controller 返回的不是 `ProductDetailResponse`，而是 `ApiResponse<ProductDetailResponse>`。前端要取 `res.data.data`（第一层 `data` 是业务对象，外层还有 `code/message/traceId/timestamp`）。
  2. **`@PathVariable Long id` 的类型转换失败会变成 500，不是 400。** 实测 `GET /api/products/abc`：

     ```
     HTTP_CODE=500
     {"code":"INTERNAL_ERROR","message":"服务器内部错误","data":null,"traceId":"395be4eb..."}
     ```

     服务端日志根因（实测）：

     ```
     Caused by: java.lang.NumberFormatException: For input string: "abc"
         at java.base/java.lang.Long.parseLong(Long.java:709)
         at org.springframework.beans.propertyeditors.CustomNumberEditor.setAsText(CustomNumberEditor.java:115)
         at org.springframework.web.method.annotation.AbstractNamedValueMethodArgumentResolver.convertIfNecessary(...)
     ```

     `GlobalExceptionHandler` 里只处理了 `MethodArgumentNotValidException`、`HttpMessageNotReadableException`、`BusinessException`、`NoResourceFoundException`，**没有处理 `MethodArgumentTypeMismatchException`**，于是落到最后的 `Exception` 兜底 → 500。这是该项目的真实缺陷，也是你后续可以提 PR 修掉的点。
  3. 前端不要把「路径参数格式错误」当成后端崩溃——它只是没被正确映射成 400。

### 第 5 层：`ProductFacade#getPublishedProduct` —— 用例编排

文件：`service/src/main/java/com/example/fullstackmall/service/product/ProductFacade.java#L125-L150`

```java
@Override
public ProductDetailResponse getPublishedProduct(Long productId) {
    ProductDetailCacheLookup cacheLookup = productDetailCacheService.lookup(productId);
    if (cacheLookup.getStatus() == ProductDetailCacheStatus.HIT) {
        return cacheLookup.getResponse();
    }
    if (cacheLookup.getStatus() == ProductDetailCacheStatus.NULL_HIT) {
        ApiCode apiCode = cacheLookup.getNullApiCode();
        throw new BusinessException(apiCode, apiCode.defaultMessage(), HttpStatus.NOT_FOUND);
    }

    // MISS、DEGRADED 和 BYPASS 都回源 MySQL；Redis 不是商品的真实数据来源。
    try {
        ProductEntity product = productDbService.requirePublishedById(productId);
        CategoryEntity category = categoryDbService.requireEnabledCategory(product.getCategoryId());
        ProductDetailResponse response = toDetailResponse(product, category);
        productDetailCacheService.put(productId, response);
        return response;
    } catch (BusinessException exception) {
        if (exception.getCode() == ApiCode.PRODUCT_NOT_FOUND
                || exception.getCode() == ApiCode.CATEGORY_NOT_FOUND) {
            productDetailCacheService.putNull(productId, exception.getCode());
        }
        throw exception;
    }
}
```

- 负责什么：这是**业务编排层**。顺序固定：先看缓存 → 未命中查商品表 → 校验分类是否启用 → Entity 转 DTO → 回填缓存 → 返回。
- 缓存策略是 Cache Aside（旁路缓存），文件 `service/src/main/java/com/example/fullstackmall/service/product/cache/ProductDetailCacheService.java`：
  - key：`mall:product:detail:v1:{productId}`（`KEY_PREFIX + productId`）；
  - 正常值 TTL 10 分钟（`MALL_PRODUCT_CACHE_VALUE_TTL`），空值 TTL 30 秒（`MALL_PRODUCT_CACHE_NULL_TTL`）；
  - 空值标记前缀 `__NULL__:`，用于防缓存穿透；
  - Redis 读异常 → `DEGRADED`，**fail-open** 继续查 MySQL；写/删异常只记日志，不影响本次结果。
- 当前 `local` profile 下 `mall.cache.product-detail.enabled=false`（`application-local.yml#L23-L27`），所以 `lookup` 直接返回 `BYPASS`，代码走到 MySQL 分支，**本次请求没有访问 Redis**。
- 前端视角最容易误解：
  1. **「商品详情缓存」不影响响应结构。** 命中缓存返回的也是同一个 `ProductDetailResponse`，字段一样；前端不该根据「是不是缓存」做任何分支。
  2. **未上架商品返回 404，不是 403。** `requirePublishedById` 只查 `status_code = 'ON_SALE'`，草稿/下架商品在公开接口里等于「不存在」。实测 `GET /api/products/3`（`OFF_SHELF`）→ `404 PRODUCT_NOT_FOUND`。
  3. 前端如果自己做「先列表拿 id，再详情」的流程，商品被下架后详情会突然 404——这是设计如此（可见性由服务端强制），不是 bug。

### 第 6 层：`ProductDbService` —— 数据访问

文件：`service/src/main/java/com/example/fullstackmall/service/product/service/ProductDbService.java#L27-L46`

```java
@Service
public class ProductDbService extends ServiceImpl<ProductMapper, ProductEntity> {

    public ProductEntity requirePublishedById(Long productId) {
        ProductEntity product = lambdaQuery()
                .eq(ProductEntity::getId, productId)
                .eq(ProductEntity::getStatusCode, ProductStatus.ON_SALE.name())
                .one();
        if (product == null) {
            throw productNotFound();
        }
        return product;
    }

    private BusinessException productNotFound() {
        return new BusinessException(
                ApiCode.PRODUCT_NOT_FOUND,
                ApiCode.PRODUCT_NOT_FOUND.defaultMessage(),
                HttpStatus.NOT_FOUND
        );
    }
}
```

- 负责什么：把「按 id + 状态查一条商品」翻译成 MyBatis-Plus 的 Lambda 条件；查不到就抛业务异常（而不是返回 `null` 让上层判空）。
- `ServiceImpl<ProductMapper, ProductEntity>` 是 MyBatis-Plus 的通用 CRUD 基类，`lambdaQuery()` 来自它。
- 对比同文件的 `requireById`（L29-35）用的是 `getById(productId)`，**只按主键查、不校验状态**——后台接口用它，公开接口用 `requirePublishedById`。这是「同一个表、两套可见性规则」的典型写法。
- 前端视角最容易误解：**「查不到」在后端是异常，不是 `null`。** 前端拿到的是 404 + `PRODUCT_NOT_FOUND`，不是 200 + `data: null`。

### 第 7 层：`ProductMapper` + MyBatis-Plus —— SQL 从哪来

文件：`service/src/main/java/com/example/fullstackmall/service/product/mapper/ProductMapper.java`

```java
public interface ProductMapper extends BaseMapper<ProductEntity> {
}
```

**没有 XML，没有 `@Select` 注解，没有手写 SQL。** 全部由 MyBatis-Plus 根据实体注解生成：

文件：`service/src/main/java/com/example/fullstackmall/service/product/entity/ProductEntity.java#L14-L47`

```java
@Data
@TableName("mall_product")
public class ProductEntity {
    @TableId(value = "id", type = IdType.AUTO)
    private Long id;

    @TableField("category_id")
    private Long categoryId;

    private String title;
    private String subtitle;
    private String description;

    @TableField("status_code")
    private String statusCode;

    @TableField("created_by")
    private Long createdBy;
    @TableField("created_at")
    private LocalDateTime createdAt;
    @TableField("updated_at")
    private LocalDateTime updatedAt;
}
```

实际执行的 SQL 等价于：

```sql
SELECT id, category_id, title, subtitle, description, status_code, created_by, created_at, updated_at
FROM mall_product
WHERE id = 1 AND status_code = 'ON_SALE';
```

- 负责什么：`ProductEntity::getId` 这种「方法引用」会被 MyBatis-Plus 反射解析成列名（`id` / `status_code`），这也是为什么字段加了 `@TableField` 时要写数据库列名。
- 前端视角最容易误解：**Java 字段名和数据库列名不是一回事。** `categoryId` ↔ `category_id`、`statusCode` ↔ `status_code`，靠 `mybatis-plus.configuration.map-underscore-to-camel-case: true`（`application.yml#L31`）自动映射。前端看到的 JSON 字段是 Java 字段名（驼峰），不是数据库列名（下划线）。

- 负责什么：Druid 管理连接（复用、校验 `SELECT 1`）；JDBC 驱动把 SQL 发给数据库；H2 在内存里建表并灌数据。
- **H2 里的数据从哪来（实测依据）**：不是 MySQL，也不是你手动导入的 `sql/01_schema.sql`。启动时 `spring.sql.init` 自动执行两个 classpath 脚本：
  - `service/src/main/resources/db/local-schema.sql`（6,124 字节，建 8 张表）
  - `service/src/main/resources/db/local-data.sql`（3,245 字节，插入种子数据）
  - 所以列表接口的 `total=2` 来自 `local-data.sql#L14-L18` 中 4 条商品里的 2 条 `ON_SALE`（`id=1`、`id=4`）；`id=2` 是 `DRAFT`、`id=3` 是 `OFF_SHELF`，公开接口都查不到。
  - 内存库 + `DB_CLOSE_DELAY=-1`：进程重启后数据重置回种子状态。
- 前端视角最容易误解：
  1. **「数据库有数据」≠「接口有数据」。** 接口有 WHERE 条件（`status_code = 'ON_SALE'`），4 条商品只出 2 条。
  2. local profile 下改数据不会持久化；重启后回到 `local-data.sql` 的状态。正式库（MySQL 3308）才需要导入 `sql/01_schema.sql` + `sql/02_seed.sql`。
  3. 端口 3308 不是默认的 3306，前端/运维如果直接连数据库容易连错。

### 第 9 层：`CategoryDbService` —— 第二个数据源

文件：`service/src/main/java/com/example/fullstackmall/service/category/service/CategoryDbService.java#L26-L40`

```java
public CategoryEntity requireCategory(Long categoryId) {
    CategoryEntity category = getById(categoryId);
    if (category == null) throw categoryNotFound();
    return category;
}

public CategoryEntity requireEnabledCategory(Long categoryId) {
    CategoryEntity category = requireCategory(categoryId);
    if (category.getStatus() != ENABLED) throw categoryNotFound();
    return category;
}
```

- 负责什么：商品详情不是只查一张表。商品表只有 `category_id`，分类名要第二次查 `mall_category`，并校验该分类当前是否启用（`status = 1`）。
- 因此一次详情请求通常是 **2 条 SQL**（商品 1 条 + 分类 1 条）。
- 前端视角最容易误解：**`categoryName` 不是商品表字段。** 它是查询时从分类表组装的。分类被停用后，即使商品还在 `ON_SALE`，详情也会 404（`CATEGORY_NOT_FOUND`）。前端不要缓存「分类名」当作商品自身属性。

> 列表接口是另一条路径：`ProductFacade#toPageResponse`（L164-180）先收集本页所有 `categoryId`，再 `findCategoryMap` 批量查一次分类，用 Map 组装，**避免 N+1**。这是列表和详情在实现上的真实差异。

### 第 10 层：Entity → DTO

文件：`ProductFacade#toDetailResponse`（L193-206）

```java
private ProductDetailResponse toDetailResponse(ProductEntity product, CategoryEntity category) {
    return new ProductDetailResponse(
            product.getId(),
            product.getCategoryId(),
            category.getName(),                       // 来自另一张表
            product.getTitle(),
            product.getSubtitle(),
            product.getDescription(),
            ProductStatus.valueOf(product.getStatusCode()),   // String → 枚举
            product.getCreatedBy(),
            product.getCreatedAt(),
            product.getUpdatedAt()
    );
}
```

DTO 定义：`contract/src/main/java/com/example/fullstackmall/contract/product/ProductDetailResponse.java`

关键差异：

| 层 | 类型 | `status` 字段 |
|---|---|---|
| 数据库 | `mall_product.status_code VARCHAR` | `'ON_SALE'`（字符串） |
| 实体 | `ProductEntity.statusCode` | `String` |
| 对外 DTO | `ProductDetailResponse.status` | `ProductStatus` 枚举 |

- 前端视角最容易误解：**DTO 和 Entity 是两套类型，不是「同一个对象换个名字」。** Entity 贴着表结构（`statusCode: String`）；DTO 贴着 API 契约（`status: ProductStatus` 枚举，序列化成 `"ON_SALE"`）。前端拿到的 `status` 是枚举名，可以直接做 `switch`，但不要假设后端表里也是枚举。

### 第 11 层：统一返回体 `ApiResponse`

文件：`contract/src/main/java/com/example/fullstackmall/contract/common/ApiResponse.java#L32-L40`

```java
public static <T> ApiResponse<T> success(T data, String traceId) {
    return new ApiResponse<>(
            ApiCode.SUCCESS.name(),          // "SUCCESS"
            ApiCode.SUCCESS.defaultMessage(),// "操作成功"
            data,
            traceId,
            Instant.now()                    // 响应时间，UTC
    );
}
```

字段：`code` / `message` / `data` / `traceId` / `timestamp`。

- 前端视角最容易误解：
  1. **业务对象在 `data` 里，外面还包一层。** 商品字段是 `res.data.data.id`，不是 `res.data.id`。
  2. `code` 是稳定业务码（`ApiCode` 枚举），`message` 是给人看的文案。**分支判断用 `code`，不要匹配中文文案**——文案随时会改。
  3. `timestamp` 是 UTC `Instant`（`2026-11-03T10:00:19Z`），而商品里的 `createdAt` 是 `LocalDateTime`（`2026-07-07T09:00:00`，无时区）。两者语义不同，前端格式化时要分开处理。

### 第 12 层：异常 → HTTP 状态码

文件：`service/src/main/java/com/example/fullstackmall/service/common/exception/GlobalExceptionHandler.java`

| 异常 | Handler 方法 | HTTP | `code` | 实测 |
|---|---|---|---|---|
| `MethodArgumentNotValidException`（`@Valid` 校验失败） | `handleValidation` | 400 | `VALIDATION_ERROR` + `fieldErrors[]` | `pageSize=101` → 400，`{"field":"pageSize","message":"每页数量不能大于 100"}` |
| `HttpMessageNotReadableException`（JSON 语法/类型错误） | `handleMalformedJson` | 400 | `MALFORMED_JSON` | 未实测（GET 无 body） |
| `BusinessException`（可预期业务失败） | `handleBusinessException` | 由异常自带（404/409 等） | 原业务码 | `id=999` → 404；`id=3`（下架）→ 404 |
| `NoResourceFoundException`（路径不存在） | `handleNotFound` | 404 | `NOT_FOUND` | 未实测 |
| 其他 `Exception` | `handleUnknownException` | **500** | `INTERNAL_ERROR` | `/api/products/abc` → 500（真实缺陷） |

- 负责什么：把所有异常收敛成统一响应体，并把堆栈只写服务端日志（`log.error("未处理的服务端异常，traceId={}", traceId, exception)`），避免把内部实现泄露给前端。
- 前端视角最容易误解：
  1. **HTTP 状态码和业务码是两套东西，但这里做了对应。** 业务失败是 404/400/409，不是「永远 200 + code」。前端 `axios` 拦截器要同时看 `error.response.status` 和 `response.data.code`。
  2. 500 时 `data` 是 `null`，`message` 是「服务器内部错误」——**不要把它当业务提示展示给用户**，应该展示兜底文案并上报 `traceId`。
  3. 参数类型错误（`/api/products/abc`）被兜底成 500，说明**异常映射表是有遗漏的**。这是可以修的：给 `GlobalExceptionHandler` 加 `MethodArgumentTypeMismatchException` → 400。

## 3. 这次请求的「事务」问题

`getPublishedProduct` 全程**没有 `@Transactional`**。

- 它做了 2 次独立查询（商品 + 分类），两次之间没有事务包裹。理论上，查完商品、查分类前分类被停用，仍会返回 404（因为第二次查询会校验 `status`）。
- 也就是说：**只读查询靠「每次查询都带条件 + 校验」保证一致性，而不是靠事务快照。**
- 对比下单链路 `OrderCreateTransactionService#createOrder` 才是 `@Transactional(rollbackFor = Exception.class)`——「锁库存 → 写订单 → 删购物车」必须整体回滚。**这是读路径和写路径在事务上的真实差异，前端视角下最容易把「接口一次调用」误认为「后端一个事务」。**

## 4. 一句话总结每一层

| 层 | 一句话职责 | 前端最容易误解的点 |
|---|---|---|
| Tomcat | 进程 + 端口 + HTTP 解析 | 服务停了就是连接被拒，不是接口报错 |
| Filter | traceId、认证授权、CORS | 401/403/CORS 拦截发生在业务代码之前 |
| DispatcherServlet | URL → 方法 | 服务端路由表，与 Vue Router 无关 |
| Controller | 接参、调用、包返回体 | 返回是 `ApiResponse<T>`，业务数据在 `data.data` |
| Facade | 用例编排、缓存、DTO 组装 | 404 是「不可见」的设计，不是 bug |
| DbService | 条件查询、抛业务异常 | 查不到 = 异常 = 404，不是 `data: null` |
| Mapper | 生成 SQL | 无 XML；驼峰 ↔ 下划线靠配置自动映射 |
| JDBC/DB | 连接池、执行 SQL | local 是 H2 内存库，数据来自 `local-data.sql` |
| DTO | 对外契约 | Entity ≠ DTO；`status` 是枚举不是字符串 |
| ApiResponse | 统一信封 | `code` 才是判断依据，`message` 是文案 |
| ExceptionHandler | 异常 → HTTP 状态 | 类型错误目前会变 500（真实缺陷） |
